# Real-time Continue Watching for ZEE5, on LaserData

Every playback heartbeat reaches the viewer's resume point in milliseconds, so a switch from TV
to phone picks up where they stopped, with heartbeats sent more often than once a minute. It runs
beside Confluent Cloud and ScyllaDB, so nothing else has to move.

This kit lets your team measure that in 15 minutes on a laptop, with Apache Iggy 0.9.0, the
open-source engine LaserData builds and runs.

- **Write-up:** https://claude.ai/artifact/Rrvarsp769dg8Fq95geKVi
- **One slide:** [`LaserData_ZEE5_ContinueWatching.pdf`](LaserData_ZEE5_ContinueWatching.pdf)

## Why this use case

From ZEE5's own talks and its then CTO:

- A heartbeat is a periodic request during playback that records what a viewer is watching and how
  far they have got; each client sends one every 60 seconds. More than 100B a day, daily peak
  concurrency of about 1M. Uses: Continue Watching ("pause on one device and resume on another"),
  concurrent viewership, top shows. Heartbeat service → heartbeat topic → playback stream
  processing → ScyllaDB; viewership rows keyed by user and asset with a 60 s TTL. ("Tracking
  Millions of Heartbeats on ZEE's Streaming Platform", Srinivas Shanmugam and Jivesh Threja; Feb
  2026 write-up.)
- Kafka on Confluent Cloud, with ksqlDB joining heartbeats to program metadata (Kafka Summit
  Bangalore 2024 session).
- "When we needed to sample more heartbeats per minute, our costs started to rise immediately."
  (Kishor Krishnamurty, then CTO; Frontier Enterprise, Aug 2024.) "The linear cost escalation
  limited us in terms of what frequency we could run these kinds of solutions like heartbeat."
  (ScyllaDB Summit keynote, Mar 2024.)

So the heartbeat interval is a cost decision, and Continue Watching pays for it. When the player
sends a final heartbeat on stop, the resume point is exact. When it does not (app closed, TV off at
the wall, network gone), the last periodic heartbeat is all there is, and at one a minute the
viewer resumes up to 60 seconds back. This kit runs that one lane on Apache Iggy, beside Confluent
Cloud: heartbeats keyed by viewer into a resume point per viewer and title. It prints the lane's
p99 every second and checks every device switch against where the viewer really stopped.

## Run it

Needs Docker and Python 3.10+. Defaults: 200,000 viewers across 5,000 titles (a long tail, like a
weekly top-shows list), a heartbeat every 10 s (20,000 a second), 15% of stops without a final
heartbeat, and a switch to another device (TV, Android, iOS, web) 2 to 20 seconds after stopping.
For a million viewers, run five `viewers.py` processes side by side with `--first 0`,
`--first 200000` and so on, each on its own core.

```
docker compose up -d                 # Apache Iggy 0.9.0 on :8090
pip install -r requirements.txt      # apache-iggy 0.9.0
python viewers.py &                  # viewers, heartbeats, device switches, and the resume check
python continue_watching.py          # resume points per viewer and title, and resume answers
```

Both print a line a second:

```
[continue-watching]  20,000 heartbeats/s  heartbeat-to-resume-point p50 …ms  p99 …ms  p99.9 …ms  PASS (<100ms)
                     viewers with a resume point …  resume requests answered …
[viewers]  20,000 heartbeats/s  watching …  resumes …  at the stop point …%  from an earlier heartbeat …%
           rewatch avg …s max …s  lane-late 0  no position 0  resume answer p99 …ms
```

`viewers.py` knows exactly where each viewer stopped. For every resume it checks the answer from
`continue_watching.py`: did playback resume at the stop point, or from an earlier heartbeat, and how
many seconds must the viewer watch again? `lane-late` counts answers built on a heartbeat older
than the latest one the player had already sent: the cost of a slow lane. Add `--why` to
`continue_watching.py` to split the latency into heartbeat-to-broker and broker-to-service.

**What the numbers mean.** The kit times each heartbeat from the moment `viewers.py` stamps it to
the moment `continue_watching.py` has applied it, through Python clients, on whatever machine you
run it on. On a shared 2-vCPU CI runner with the broker and all scripts on one box, at 2,000
heartbeats/s (20,000 viewers, one every 10 s), with the service reading every heartbeat partition
directly, two runs held p50 4.1 to 5.7 ms, p99 7.2 to 10.0 ms and p99.9 7.9 to 10.7 ms (median of 57
steady-state seconds each), with no failing second. About 1,100 to 1,200 device switches were checked
per run: 86.0% and 86.7% resumed at the stop point (median per second; the rest were the stops the kit
sends without a final heartbeat), the average rewatch was 0.6 s, no answer was built on a heartbeat the
lane had not delivered, and resume answers came back with p99 13.2 to 13.7 ms. A content-metadata burst
on a neighbouring topic, generated by a Python script on the same two CPUs, reached about 1.0 MB/s (500
records/s, twenty times its steady rate in CI) and left the lane's p99 where it was (6.9 to 7.0 ms,
9.7 to 10.0 ms). That is the end-to-end lane through this demo
code, not the broker alone, and it does not include the mobile network. The broker's own tail
latency is measured with `iggy-bench` in `bench/PLAN.md`, on dedicated machines.

| File | What it is |
|---|---|
| `viewers.py` | Viewers playing titles on TV, Android, iOS and web: a heartbeat every `--every` seconds keyed by viewer ID to `heartbeats`, with a per-viewer sequence and the position itself; a final `stop` heartbeat unless the app is closed first; a resume request from another device a few seconds later. Checks every answer against the truth. |
| `continue_watching.py` | The Continue Watching service: a resume point per viewer and title from the newest heartbeat; answers each resume request on `resume-answers` with the position and the heartbeat it came from. Rebuilds by replaying the retained heartbeats. |
| `content_publish.py` | A neighbour on the same broker: content metadata (titles, descriptions, subtitles, languages) at a steady rate, then 20× for a minute, like a big release. |
| `kafka_bridge.py` | Copies your existing heartbeat topic from Confluent Cloud into Iggy through its own consumer group, for a shadow run on real traffic. |
| `bench/PLAN.md` | The benchmark we run with you; rules fixed before results. |

## Three tests

1. **Evening peak:** `python viewers.py --peak 3 --peak-at 60 --peak-for 120` (three times the
   viewers for two minutes). Pass: heartbeat-to-resume-point p99 under 100 ms, and `lane-late`
   stays at 0.
2. **A release drop next door:** `python content_publish.py --rate 500 --x 20` while both run.
   Pass: the lane's p99 moves by less than 10%. The script prints the rate it actually reached.
3. **Today's interval, then a shorter one:** `python viewers.py --every 60`, then `--every 10`.
   Pass: resumes at the stop point stay the same, and the rewatch after stops with no final
   heartbeat falls with the interval (about 30 s at 60 s, about 5 s at 10 s). The evaluation then
   prices each interval on each side.

Restart `continue_watching.py` at any time: it replays the retained heartbeats (24 hours by
default), prints "catching up" until a whole second of heartbeats arrives inside the budget, and
then answers from the rebuilt resume points.

## Shadow your own traffic

```
pip install confluent-kafka
python kafka_bridge.py --bootstrap <cluster>.confluent.cloud:9092 --kafka-topic <heartbeat-topic> \
  -X security.protocol=SASL_SSL -X sasl.mechanisms=PLAIN -X sasl.username=<api-key> -X sasl.password=<api-secret>
python continue_watching.py
```

The bridge joins your heartbeat topic as its own consumer group, `iggy-shadow`, so the heartbeat
service, ksqlDB, the ScyllaDB connectors and every consumer you run today are untouched. Map your
record shape in `to_msg()`: the kit needs `k` (viewer or profile ID), `asset`, `pos`, and `ev` if
your players send a final heartbeat; a per-viewer sequence is added if your records do not carry
one. With real heartbeats, `continue_watching.py` reports heartbeat-to-resume-point latency
straight away; to check its answers, compare them with the resume points ScyllaDB serves today.
