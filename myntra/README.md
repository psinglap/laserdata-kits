# Real-time session context for Myntra search suggestions, on LaserData

Every search, product view and bag add reaches the shopper's session context in milliseconds, so the next
type-ahead suggestions lead with what they want now. It runs beside your Kafka, so nothing else has to move.

This kit lets your team measure that in 15 minutes on a laptop, with Apache Iggy 0.9.0, the
open-source engine LaserData builds and runs.

- **Write-up:** https://claude.ai/artifact/A674Dn6Tu3dXoLFVokeLwC#p.myntra-kit
- **One slide:** [`LaserData_Myntra_SessionContext.pdf`](LaserData_Myntra_SessionContext.pdf)

## Why this use case

From Myntra's own sources:

- Myntra built contextual type-ahead on a short-term context: "We want to provide smart type-ahead
  suggestions, based on short-term user activity context." Each event becomes annotations (category,
  brand, with weights); "Context grows with every user signal, or else decays over time"; the pipeline is
  Kafka, then an Apache Storm topology with a batching bolt, then a user context in Redis that boosts Solr
  suggestions. The A/B test showed "an increase of 3% in CTR for contextual type-ahead users" (Myntra
  Engineering, Nov 2018).
- The Near Real Time team still runs personalized search auto-suggest: "the user's input needs to be
  analyzed at very low latency to provide instant results that are personalized to the user". Myntra's
  "clickstream Kafka is responsible for ingesting billions of events that are generated by users every
  day", 18.8 billion app and web events on BFF 2022's first day (Myntra Engineering, May 2023).
- Today the ML platform serves "user embeddings, session context, product vectors, and trend signals" from
  Aerospike, fed by Spark Streaming, inside "a 50-millisecond recommendation latency budget", with
  "millions of clickstream events each minute" and half a million concurrent users at sale peaks
  (Aerospike blog, Mar 2026, with Myntra's Principal Architect for Data and ML Platform).
- Myntra's Kafka platform Airbus serves "100+ clients" with billions of messages a day, and Kafka feeds the
  real-time feature store for "personalization, search ranking, and widget reordering" (Kafka Summit
  Bangalore 2024). Myntra's move from batch to Kafka and Spark Structured Streaming cut latency "from hours
  to mere minutes" at "millions of events/minute" (Current Bengaluru 2025).

Your clickstream Kafka, Spark Streaming and Aerospike are the right home for billions of events a day,
and this kit does not touch them. The session context behind a type-ahead request is a narrower job with
a tighter clock: a shopper opens a kurta, goes back to the search bar and types "ku" a second later. A
batching bolt or a micro-batch holds that action until the batch closes. This kit runs shopper actions
on their own lane, keyed by user, read by the context service directly, and counts the outcome:
type-ahead requests boosted without the shopper's last action.

Myntra does not publish today's type-ahead context path, its batch interval, or the gap from an action
to the next search. The lane is a proposal; the kit's flags let you set those to yours.

## Run it

Needs Docker and Python 3.10+. Defaults: 500,000 shoppers in session, 20,000 shopper actions a second
(search, product view, wishlist, bag add, filter), a 30% chance a shopper changes intent, half of the
actions followed by a type-ahead request 0.3 to 2 s later, and a 2× sale-opening surge for the first
minute. These are illustrative; set them to yours.

```
docker compose up -d                   # Apache Iggy 0.9.0 on :8090
pip install -r requirements.txt        # apache-iggy 0.9.0
python context.py &                    # the session context service, boosting every type-ahead request
python app.py &                        # shoppers browsing and searching
python clickstream.py --at 20          # a heavy clickstream next door
```

Each prints a line a second:

```
[app]  40,000 shopper actions/s (surge)  search …  view …  wishlist …  bag …  filter …  intent changes …  type-ahead requests …
[context]  40,000 actions/s  action-to-context p50 …ms  p99 …ms  p99.9 …ms  PASS (<50ms)  shoppers in context …
[type-ahead] requests …  lead category changed …  boosted without the last action …%  wrong category boosted …
```

`boosted without the last action` is the business number. Each action carries its annotations
(category, brand, gender, weighted by action type, as in Myntra's contextual type-ahead) with the
shopper's session and a sequence that only grows per user. The context service folds them into a
decaying session context, the same way in every script (`common.fold()`). Each type-ahead request
carries the sequence of the shopper's last action and the category the context should lead with after
it. `context.py` asks whether it had applied that action when the request started. If not, the
suggestions were boosted from a stale context; if the stale context leads with another category, the
shopper saw suggestions for what they wanted a moment ago (`wrong category boosted`).

What-if: `python context.py --hold-ms 1000` applies every action only once it is 1 s old, as a
one-second batch window would, so you can see how many requests such a path boosts from a stale context.

**What the numbers mean.** The kit times each action from the moment `app.py` sends it to the moment
`context.py` has folded it into the context, through Python clients, on whatever machine you run it on.
On a shared GitHub runner (2 vCPU), with the broker and four Python processes on one box, at 1,500 shopper
actions a second over 200,000 shoppers (2x for 15 s as the surge), two green CI runs held p50 7.0 to 8.1 ms,
p99 12.2 to 14.9 ms and p99.9 14.2 to 16.8 ms (median per second over 62 steady-state seconds each, no second
over the 50 ms budget). Through the surge (3,000 actions a second) the median per-second p99 was 16.5 to
19.4 ms, worst 18.7 to 21.4 ms, with a 1 MB/s clickstream next door. Of about 57,400 to 57,800 type-ahead
requests per run, none was boosted without the shopper's last action and no wrong category was boosted. The
what-if with every action applied 1 s late boosted 40.9 to 41.0% of requests (median per second) from a stale
context, about 8,800 to 8,900 per run leading with the wrong category. That is the end-to-end lane through
this demo code at reduced scale, not the broker alone; the broker's own tail latency is measured with
`iggy-bench` on dedicated machines (`bench/PLAN.md`).

| File | What it is |
|---|---|
| `app.py` | The Myntra app: shopper actions on `shopper-actions` (weighted annotations, session, sequence only grows per user), and the shopper's next type-ahead request on `typeahead-requests`. `--gap-min/--gap-max`, `--switch-share` and `--surge` shape the load. |
| `context.py` | The session context service: folds actions by sequence, times action-to-context, boosts every type-ahead request and checks it against the shopper's last action. `--hold-ms` is the what-if. |
| `common.py` | Topics, partitioning by user, and the context fold (decay, weights, eight annotations per shopper). |
| `clickstream.py` | A bulk, latency-tolerant clickstream (page loads, impressions) on its own topic on the same broker. |
| `kafka_bridge.py` | Reads your shopper events from Kafka as consumer group `iggy-shadow`, read-only, and publishes them to the lane, keyed by user, for a shadow run on real traffic. |
| `bench/PLAN.md` | The benchmark we run with you; rules fixed before results. |

## Three tests

1. **A sale opens:** `python app.py --actions-per-s 20000 --surge 2 --surge-for 60`.
   Pass: action-to-context p99 under 50 ms through the surge, and no request boosted without the last action.
2. **Clickstream on the same broker:** `python clickstream.py --mbps 20 --at 20`.
   Pass: the lane's p99 moves by less than 10% while it runs.
3. **Restart the context service:** stop `context.py` and start it again. It rebuilds every shopper's
   context from the lane, prints "catching up", then times live actions again.
   Pass: no action applied twice, back under budget within seconds.

## Shadow your own traffic

```
pip install confluent-kafka
python kafka_bridge.py --bootstrap <your-brokers> --kafka-topic <your-user-context-events>
```

The bridge only reads, as its own consumer group (`iggy-shadow`); the app, the event collector, every
producer and every existing consumer, Storm topology and Spark job are untouched. Map your fields in
`to_action()`: the defaults read the event contract from Myntra's contextual type-ahead post (`userid`,
`annotations` with `field`, `value` and `weight`, `timestamp`, `source`). In shadow mode the clock starts
when the bridge reads the record. Everything runs in your Azure subscription.
