# Real-time driver location for live trip tracking at Porter, on LaserData

Every driver-partner's location ping reaches the live tracking link and the pickup and drop
arrival checks in milliseconds, for two-wheelers and trucks alike, even in a booking surge. It
runs beside Cloud Pub/Sub, so PostGIS, the order services and everything else stay where they are.

This kit lets your team measure that in 15 minutes on a laptop, with Apache Iggy 0.9.0, the
open-source engine LaserData builds and runs.

- **One slide:** [`LaserData_Porter_TripTracking.pdf`](LaserData_Porter_TripTracking.pdf)

## Why this use case

From Porter's own words:

- "Porter migrated 130+ PostgreSQL databases to Cloud SQL for PostgreSQL, leveraging PostGIS and
  Cloud Pub/Sub to process real-time geospatial telemetry pings from active drivers." And:
  "We wanted to optimize our cloud costs while modernizing our infrastructure with Kubernetes."
  (Bijoy Paul, Principal Engineer; Google Cloud customer story)
- "Real time order statuses and the live location of the partner on the map can be tracked
  through the tracking link shared on the sender and receiver phone numbers"; business customers
  get order statuses by webhook at Accepted, Live, Ended, Reopened and Cancelled (Porter API
  integrations page).
- On-demand mini-trucks, tempos and two-wheelers in 50+ cities; "high-demand booking surges"
  (Google Cloud customer story). More than 500,000 orders a day, 60% of them on two-wheelers
  (The Ken, Sep 2025); 3 lakh driver-partners a month (Inc42, Aug 2026).

So whether the sender and receiver see where their goods really are, and hear that the driver has
reached the pickup or the drop when it happens, depends on how fresh the driver's position is
when each reader gets it. Driver pings are the highest-rate stream in a trip and only useful for
minutes. This kit runs that one lane on Apache Iggy, on its own, and prints its p99 every second.

## Run it

Needs Docker and Python 3.10+. Defaults: 20,000 driver-partners online in Bengaluru (60%
two-wheelers, the rest three-wheelers, mini-trucks and 8 ft pickups), a ping
every 5 s (4,000 pings/s), half of them waiting near KR Market, Chickpet, Yeshwanthpur APMC,
Peenya and Electronic City; loading and unloading take longer the bigger the vehicle.

```
docker compose up -d                 # Apache Iggy 0.9.0 on :8090
pip install -r requirements.txt      # apache-iggy 0.9.0
python drivers.py &                  # drivers on the road: pings, order lifecycle, and the arrival check
python trips.py                      # live trip service: tracking links and pickup/drop arrivals
```

Both print a line a second:

```
[trips]    4,000 pings/s  ping-to-tracker p50 …ms  p99 …ms  p99.9 …ms  PASS (<200ms)  open orders …
           tracking-link position age p99 …s  arrivals reached_pickup … reached_drop …
[drivers]  4,000 pings/s  online 20,000  on a trip …  arrivals checked …  on the first ping inside the fence …%
           one ping late …%  two or more late …%  missed …  ping-to-notice p99 …ms
```

`drivers.py` knows, for every order, which ping was the first one inside 150 m of the pickup and
of the drop. It checks every arrival `trips.py` publishes: was it fired on that ping, or one or
more pings late, and how long after the driver's phone created the ping did the notice exist?
Each ping late is about five more seconds of "on the way" for a driver who is already at the
gate. Add `--why` to `trips.py` to split the latency into ping-to-broker and broker-to-tracker.

**What the numbers mean.** The kit times each ping from the moment `drivers.py` creates it to the
moment `trips.py` has applied it, through Python clients, on whatever machine you run it on. On a
shared 2-vCPU CI runner with the broker and all scripts on one box, at 2,000 pings/s (10,000
drivers, road time running 3× so trips reach their fences inside the minute), three runs held
p50 12 to 16 ms, p99 24 to 31 ms and p99.9 26 to 36 ms (median of 59 steady-state seconds each),
with no failing second. About 4,350 arrivals were checked per run, with ping-to-notice p99 of 47
to 53 ms; in the last two runs every one was fired on the first ping inside the fence (the first
run had one arrival a ping late, from rounding at the fence edge in the kit's own truth check,
since fixed). A 20× log burst on a neighbouring topic, generated by a Python script on the same
two CPUs, moved the lane's p99 by -1% to +79% depending on the run (24.4 to 24.2 ms, 27.3 to
48.9 ms, 26.8 to 38.9 ms). That is the end-to-end lane through this demo code, not the broker
alone, and it does not include the mobile network. The broker's own tail latency is measured
with `iggy-bench` in `bench/PLAN.md`, on dedicated machines.

| File | What it is |
|---|---|
| `drivers.py` | Driver-partners in Bengaluru by vehicle class: idle near markets, driving to pickups, loading, driving to drops, unloading. Pings keyed by driver ID to `driver-pings`, with a per-driver sequence and the position itself; `accepted`, `live` and `ended` to `trip-events`. Checks every arrival against the truth. |
| `trips.py` | The live trip service: each open order's tracking-link view (status, latest position, its age) and the 150 m fence check on every ping; `reached_pickup` and `reached_drop` to `trip-milestones` with the ping they came from. |
| `log_flood.py` | A neighbour on the same broker: application log lines at a steady rate, then 20× for a minute, like a noisy deploy. |
| `pubsub_bridge.py` | Copies your existing driver-ping topic from Cloud Pub/Sub into Iggy through its own subscription, for a shadow run on real traffic. |
| `bench/PLAN.md` | The benchmark we run with you; rules fixed before results. |

## Three tests

1. **Booking surge:** `python drivers.py --peak 3 --peak-at 60 --peak-for 120` (three times the
   drivers online for two minutes). Pass: ping-to-tracker p99 under 200 ms, and arrivals two or
   more pings late under 0.1%.
2. **A log burst next door:** `python log_flood.py --mbps 0.5 --x 20` while both run. Pass: the
   lane's p99 moves by less than 10%. The script prints the rate it actually reached.
3. **Rebuild the trip service:** stop `trips.py` and start it again; it replays the retained
   pings and trip events. Pass: it catches up within seconds, and arrivals keep firing on the
   first ping inside the fence.

## Shadow your own traffic

```
pip install google-cloud-pubsub
gcloud pubsub subscriptions create iggy-shadow --topic=<your-driver-ping-topic> --message-retention-duration=1h
python pubsub_bridge.py --project <gcp-project>
```

A Pub/Sub topic delivers every message to every subscription, so the bridge's own `iggy-shadow`
subscription leaves the driver app, the publishers and every subscriber you run today (the
PostGIS writers included) untouched. Map your record shape in `to_msg()`: the kit needs `k`
(driver ID), `lat`, `lon`, and `order` if your pings carry it; the device timestamp becomes the
per-driver sequence, so Pub/Sub redeliveries and reordering cannot move a driver backwards. With
real pings, `trips.py` reports ping-to-tracker latency straight away; arrivals also need your
order events on `trip-events`.
