# Real-time captain location and matching for Rapido, on LaserData

Every on-duty captain's location ping reaches the matching engine and the customer's pickup
tracker in milliseconds, even at the office-hour peak. It runs beside Kafka, so the event bus,
the data platform and everything else stay where they are.

This kit lets your team measure that in 15 minutes on a laptop, with Apache Iggy 0.9.0, the
open-source engine LaserData builds and runs.

- **One slide:** [`LaserData_Rapido_CaptainMatch.pdf`](LaserData_Rapido_CaptainMatch.pdf)

## Why this use case

From Rapido's own words:

- "We can track that request to the nearest available two-wheeler taxi and allocate the job to
  the right rider." And on leaving multi-cloud: "Being a real-time service, we needed to provide a
  superior experience, based on low latency." (Srivatsa Katta, Google Cloud customer story, 2019)
- The matching engine handles more than 15,000 ride requests a minute, with an average allocation
  time under 15 to 20 seconds, using "real-time location signals, traffic conditions, and captain
  availability" (Rapido release, May 2026).
- Captain location is collected while a captain is On-Duty, to "receive orders close to your
  location" and to let customers "track the distance of the Captains from their location for pick
  up" (Rapido privacy policy).
- Kafka is the event bus: 2 billion+ events consumed a day by the data platform (Rapido Labs,
  2025); the message transporter publishes its events to Kafka (Rapido Labs, 2023); consumer lag
  is watched with Burrow.
- Hyderabad alone: 9.1 lakh rides a day, 4.7 lakh of them in office and college peak hours
  (company figures, Feb 2026).

So whether matching sends a ride to the captain who is actually nearest depends on how fresh the
captain's position is when the request arrives. Captain pings are the highest-rate stream in the
ride journey and only useful for minutes. This kit runs that one lane on Apache Iggy, on its own,
and prints its p99 every second.

## Run it

Needs Docker and Python 3.10+. Defaults: 50,000 captains on duty in Hyderabad, a ping every 5 s
(10,000 pings/s), 2,000 ride requests a minute, most of them from HITEC City, Gachibowli,
Madhapur, Ameerpet and Secunderabad.

```
docker compose up -d                 # Apache Iggy 0.9.0 on :8090
pip install -r requirements.txt      # apache-iggy 0.9.0
python captains.py &                 # captains on duty, ride requests, and the offer check
python match.py                      # nearby-captain index, offers, pickup tracking
```

Both print a line a second:

```
[match]  10,000 pings/s  ping-to-index p50 …ms  p99 …ms  p99.9 …ms  PASS (<200ms)  requests …/s  offers …
         no captain in 3 km …  request-to-offer p99 …ms  free in index …  pickup-track …
[captains] 10,000 pings/s  on duty 50,000  on a ride …  requests …/s  offers checked …  on the latest ping …%
         one ping behind …%  two or more behind …%  pickup distance off >250 m …%  offered while busy …
```

`captains.py` knows every ping it has sent and where every captain really is, so it checks each
offer the matcher publishes: was it computed on the captain's latest ping, or on one the captain
had already replaced, and how far off was the pickup distance? That is the business cost of a
slow lane: a captain further away than matching thought, a longer allocation and more dead
kilometres.

**What the numbers mean.** The kit times each ping from the moment `captains.py` creates it to
the moment `match.py` has applied it to the index, through Python clients, on whatever machine
you run it on. On a shared 2-vCPU CI runner with the broker and all scripts on one box, at
2,000 pings/s (10,000 captains) and 10 ride requests a second, two runs held p50 12.5 ms,
p99 25 to 27 ms and p99.9 26 to 31 ms (median of 59 steady-state seconds each), with no failing
second; request-to-offer p99 was 9 to 11 ms, and every offer was computed on the captain's latest
ping. A 20× comms-event burst on a neighbouring topic, generated by a Python script on the same
two CPUs, moved the lane's p99 from 24.9 to 24.4 ms in one run and from 26.0 to 30.5 ms in the
other. That is the
end-to-end lane through this demo code, not the broker alone, and it does not include the mobile
network. The broker's own tail latency is measured with `iggy-bench` in `bench/PLAN.md`, on
dedicated machines.

| File | What it is |
|---|---|
| `captains.py` | Captains on duty in Hyderabad, drifting towards demand when free, riding to pickups and drops when not. Pings keyed by captain ID to `captain-pings`, with a per-captain sequence, the position itself and free/busy; ride requests to `ride-requests`. Checks every offer against the truth. |
| `match.py` | The nearby-captain index (~1 km cells, a stand-in for the hex cells matching uses): nearest free captain within 3 km of each pickup, offers to `ride-offers` with the ping they used, and distance-to-pickup updates on `pickup-track`. |
| `comms_burst.py` | A neighbour on the same broker: message transporter events (`message_created`, `message_pushed_to_mobile`) at a steady rate, then 20× for a minute, like a city-wide campaign. |
| `kafka_bridge.py` | Copies your existing captain-ping topic from Kafka into Iggy as a read-only consumer group, for a shadow run on real traffic. |
| `bench/PLAN.md` | The benchmark we run with you; rules fixed before results. |

## Three tests

1. **Office-hour peak:** `python captains.py --peak 3 --peak-at 60 --peak-for 120`
   (three times the ride requests for two minutes). Pass: ping-to-index p99 under 200 ms, and
   offers two or more pings behind under 0.1%.
2. **A campaign burst next door:** `python comms_burst.py --mbps 0.5 --x 20` while both run.
   Pass: the lane's p99 moves by less than 10%. The script prints the rate it actually reached.
3. **Rebuild the index:** stop `match.py` and start it again; it replays the retained pings.
   Pass: it catches up within seconds and offers return to the latest ping.

## Shadow your own traffic

```
pip install confluent-kafka
python kafka_bridge.py --bootstrap <bootstrap-servers> --kafka-topic <your-captain-ping-topic> \
  -X security.protocol=SASL_SSL -X sasl.mechanisms=SCRAM-SHA-512 -X sasl.username=<user> -X sasl.password=<password>
```

The bridge only reads, as its own consumer group `iggy-shadow`; the captain app, location
ingestion and every existing consumer are untouched. Map your record shape in `to_msg()`: the kit
needs `k` (captain ID), `lat`, `lon` and free/busy. With real pings, `match.py` reports
ping-to-index latency straight away; offers also need your ride requests on `ride-requests`.
If captain pings do not pass through Kafka today, point the bridge's source at your location
ingestion service instead.
